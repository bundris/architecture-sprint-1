# Задание 1
Требуется разбить проект Mesto (frontend) на микрофронтенды. 

## Уровень 1: Проектирование

### Выбор фреймворка
MFE будут на React, так как на нем написано начальное приложение 
и в команде нет разработчиков на других фреймворках. 

Для интеграции MFE в приложение будем использовать Webpack Module Federation, 
так как webpack более знаком как инструмент.


### Предварительный анализ
#### Сложность приложения
Приложение небольшое, команды нет и в моменте не требует перехода на MFE. 
#### Цель перехода
Основной повод к переходу на MFE - получение опыта прежде чем это придется делать на реальном проекте.
#### Опыт команды
Его нет

### Бизнес функции (БФ)
Какие БФ фронтенда можно выделить
* auth - формы авторизации и регистрации
* profile - редактирование профиля пользователя
* places - редактирование и отображение карточек (по отдельности и в галерее)

Я бы применил стратегию вертикальной нарезки по каждой из БФ. 
Это более понятные зоны ответственности, связность БФ низкая 
(на текущий момент только общий контекст в виде пользователя)

### Методы реализации и интеграции 

Предпочтение Run time с клиентской компоновкой, 
для более частых независимых обновлений. 
Скорее всего, auth и profile будут меняться существенно реже чем places. 

## Уровень 2: Планирование изменений

### Создание модулей
В папке app/frontend создаем под каждый MFE папку mf-<имя MFE>.
Список MFE - auth, places, profile, host, shared. 
для каждой БФ отдельный MFE, host для их интеграции и shared для состояния.

### Распределение компонент по модулям
| MFE name | Component           |
|----------|---------------------|
| places   | AddPlacePopup.js    |
| places   | Card.js             |
| places   | ImagePopup.js       |
| host     | App.tsx             |
| profile  | EditAvatarPopup.js  |
| profile  | EditProfilePopup.js |
| auth     | InfoTooltip.js      |
| auth     | Login.js            |
| auth     | Register.js         |
| host     | PopupWithForm.js    |
| host     | Header.js           |
| host     | Footer.js           |
| host     | Main.js             |
| host     | ProtectedRoute.js   |
| shared   | AuthProvider.js     |

В host я помещаю основной layout (header/footer/...) и popup элементы - они повсеместные 
и проще их рендерить по состоянию, чем управлять ими в каждом отдельном MFE.
В качестве межмодульного взаимодействия будем использовать CurrentUserContext, 
а его провайдером-оберткой будет AuthProvider. 
Потенциально еще можно выделить layout MFE, чтобы темплейты страниц вынести отдельно, 
но на текущем этапе это кажется избыточным.

# Задание 2

Я выделяю следующие микросервисы и компоненты:
- Панель управления - админка для техподдержки и администратора (с разделением по правам доступа).
Реализован на Next как BFF.
- Портал электронной площадки - это пользовательский интерфейс для взаимодействия с сервисами. 
Реализован на Next как BFF.
- Авторизация - проверяет пользователя, выдает JWT в зависимости от роли
- Пользователи - хранит пользовательские данные (профиль) и предоставляет возможность зарегистрироваться
- Аукционы - отвечает за операции с акционами
- Продукты - пока что я не вижу повода держать отдельные сущности для услуг и товаров, 
поэтому объединяю их в сущность "Продукт" с свойством "Тип".
- Заказы - сервис для оформления заказа. 
- Техподдержка - позволяет связаться с саппортом и 
если случилась какая-то ошибка - подать заявку на аппеляцию
- Отчеты - сервис генерации отчетов
- Оплата - принимает заказы пользователей и связывает их с внешними платежными системами. 
Также хранит последнюю полученную данную о статусе каждого заказа и транзакции. 
- Kafka - реализует очередь нотификаций
- Сервис оповещения - занимается рассылками писем/SMS/других сообщений. 

По умолчанию все бекенды предполагаются на Django/Python, 
хотя в случае микросервисов я бы по возможности заменил их на более легковесное решение
типа Flask. 
Для хранения данных каждый микросервис использует PostgreSQL как БД. 
Заказы и продукты могут быть более комплексными (содержать вложенные сущности, например), 
поэтому их я бы хранил в MongoDB.
Также пользователи могут хранить аватары (изображения), а продукты - фото и видео. 
Для хранения файлов будем использовать S3 совместимое хранилище 
(из исходной задачи непонятно, должно ли оно быть распределенным географически или нет, 
поэтому конкретное хранилище не указываю)
